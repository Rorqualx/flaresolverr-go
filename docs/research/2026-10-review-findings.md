# Primary sources confirm most FlareSolverr-Go findings

External primary sources confirm the substance of almost every finding from the FlareSolverr-Go code review, refute one sub-claim, and leave a small set of questions that only a live probe can settle. The highest-impact confirmations are that Chrome hands `ProvideCredentials` to whichever auth challenge is pending (so proxy credentials reach any origin that returns a 401), that the WHATWG URL parser reads `01200000001` as `10.0.0.1` while Go's decimal parse sees a public address, and that go-rod v0.116.2 has no timeout anywhere in its CDP call path or its launcher `Cleanup()`. No pre-navigation check can stop DNS rebinding when Chrome is the HTTP client, and Chrome's Local Network Access does not gate top-level navigations, so the sound fix is to take egress away from Chrome (network policy or a forced validating proxy). The presence of a `cf_clearance` cookie is not documented by Cloudflare as proof of a solved challenge, and no captcha provider documents a sitekey-plus-URL Turnstile token as sufficient for a managed-challenge interstitial; hCaptcha has disappeared from all three providers' public API documentation. Both Go advisories apply to the module as pinned, and Go 1.24 has been out of support since 2026-02-10. The one refuted claim is that Alpine lacks Chromium on armv7: it is built for all three shipped architectures, and the real problem is that Alpine 3.21's community repository is unsupported and the branch ends on 2026-11-01. Two caveats apply throughout: Chromium behaviour was established by reading `main`-branch source rather than the 155 release branch or a running browser, and several fix directions are reasoned from the sources rather than prescribed by them.

## Chrome gives supplied credentials to any pending challenge

### Proxy credentials leak to origins that return 401

The protocol definition gives `AuthChallenge` a `source` of `Server` or `Proxy`, and Chromium's handler builds the event from the network stack's challenge with no filtering on type, so **`Fetch.authRequired` fires for origin 401s as well as proxy 407s** ([Fetch.pdl](https://github.com/chromium/chromium/blob/main/third_party/blink/public/devtools_protocol/domains/Fetch.pdl), [fetch_handler.cc](https://github.com/chromium/chromium/blob/main/content/browser/devtools/protocol/fetch_handler.cc)). The response path has no branch on `is_proxy`: `ProcessAuthResponse` runs the pending callback with the supplied credentials whatever the source, and `ContinueWithAuth` performs no source check either ([devtools_url_loader_interceptor.cc](https://github.com/chromium/chromium/blob/main/content/browser/devtools/devtools_url_loader_interceptor.cc)). Finding 1 is therefore confirmed at the CDP layer. That the credentials then become an `Authorization` header to the origin, and are cached for that origin and realm, is an inference: the network-stack side was not traced. Any site visited through the pool triggers it by returning `401` with `WWW-Authenticate: Basic`.

No library solves this. Puppeteer answers `ProvideCredentials` whenever credentials exist and never inspects `source` ([NetworkManager.ts](https://github.com/puppeteer/puppeteer/blob/main/packages/puppeteer-core/src/cdp/NetworkManager.ts)); Playwright selects credentials by request origin but injects proxy credentials as an origin-less entry ([crNetworkManager.ts](https://github.com/microsoft/playwright/blob/main/packages/playwright-core/src/server/chromium/crNetworkManager.ts)). go-rod's `Browser.HandleAuth` is one-shot, ignores `source`, assumes the first paused request and first auth event belong together, and is the origin of the `Invalid state for continueInterceptedRequest` panics reported with authenticated proxies ([hijack.go](https://github.com/go-rod/rod/blob/v0.116.2/hijack.go), [rod #903](https://github.com/go-rod/rod/issues/903), [rod #991](https://github.com/go-rod/rod/issues/991)). It is unsuitable for a long-lived pool.

The fix direction is a hand-written dispatcher: answer `ProvideCredentials` only when `source == Proxy` (optionally also checking that `origin`, which is the challenger, matches the configured proxy) and only on the first challenge for a given `requestId`; answer `CancelAuth` otherwise. No primary source prescribes the non-proxy response. `CancelAuth` is the deterministic choice for a headful pool because the protocol describes `Default` as likely to "either Cancel authentication or display a popup dialog box". The one-attempt guard matters because Chrome re-issues the challenge when credentials are rejected, and both Puppeteer and Playwright cancel on the second event. Three preconditions shape the implementation: auth interception only applies to requests matched at the Request stage, enabling it makes every matching request emit `Fetch.requestPaused` and stall until continued, and an explicitly empty pattern list with `handleAuthRequests` is rejected ([fetch_handler.cc](https://github.com/chromium/chromium/blob/main/content/browser/devtools/protocol/fetch_handler.cc)).

### A second Fetch.enable silently replaces the first

`SetPatterns` assigns both the pattern list and `handle_auth_`, so **a second `Fetch.enable` on the same session replaces rather than merges**, and omitting `handleAuthRequests` turns auth handling off ([devtools_url_loader_interceptor.cc](https://github.com/chromium/chromium/blob/main/content/browser/devtools/devtools_url_loader_interceptor.cc)). go-rod's `HijackRouter` re-sends its own `Fetch.enable` on every `Add` and `Remove` with `HandleAuthRequests` unset, its `Stop()` sends `Fetch.disable`, and it has no `authRequired` handling at all; the source itself warns that other Fetch use should stop while the router runs ([hijack.go](https://github.com/go-rod/rod/blob/v0.116.2/hijack.go)). A second handler acting on an already-continued request gets `-32000 Invalid state for continueInterceptedRequest`. rod's `EnableDomain` also caches enable state, so a second call with different parameters is not sent at all ([states.go](https://github.com/go-rod/rod/blob/v0.116.2/states.go)). The fix is one owner of the Fetch domain per session, a single `Fetch.enable` carrying the union of patterns and the auth flag, sent with a direct proto call, and one dispatcher for both events. The exact error text for continuing a request that has already finished was not located and stays open.

### Extra headers, click coordinates, auto-attach and user-agent fields

`Network.disable` clears extra headers on both the browser and renderer sides ([network_handler.cc](https://github.com/chromium/chromium/blob/main/content/browser/devtools/protocol/network_handler.cc)). The rod-specific trap is that `Page.SetExtraHeaders` returns `EnableDomain`'s restore function, which sends `Network.disable` only if Network was not already enabled, so the cleanup removes the headers in one case and does nothing in the other ([page.go](https://github.com/go-rod/rod/blob/v0.116.2/page.go)). Clear deterministically by sending `Network.setExtraHTTPHeaders` with an empty map. The user-agent override lives in the Emulation agent, so `Network.disable` most likely leaves it in place; that was not tested.

`DOM.getContentQuads` returns quads "relative to viewport" in CSS pixels, and `Input.dispatchMouseEvent` takes viewport-relative coordinates, so **main-frame quads go to the mouse event unchanged**; adding scroll offsets is a bug that appears only once the page scrolls ([DOM.pdl](https://github.com/chromium/chromium/blob/main/third_party/blink/public/devtools_protocol/domains/DOM.pdl)). rod's own `Interactable` confirms the convention by adding `scrollX/scrollY` only when converting to document coordinates ([element.go](https://github.com/go-rod/rod/blob/v0.116.2/element.go)). Quads are not clipped, so scroll into view and re-read. The frame of reference for nodes inside out-of-process iframes and under pinch-zoom was not traced.

With `Target.setAutoAttach {waitForDebuggerOnStart: true}`, Chromium defers the navigation that creates the child frame until `Runtime.runIfWaitingForDebugger` arrives on the child session, and the code read contains no timeout ([target_handler.cc](https://github.com/chromium/chromium/blob/main/content/browser/devtools/protocol/target_handler.cc)). A session that is never resumed leaves the iframe blank, which for a Turnstile frame means the widget never renders. Send the resume on every auto-attached session, and re-issue `setAutoAttach` on each child because it is per-session and non-recursive. Whether detaching releases a deferred navigation is unverified. rod v0.116.2 never calls either command and offers no way to turn an auto-attached session id into a usable `*Page`; its default launcher flags disable site isolation outright, and an open issue documents that `Element.Frame()` evaluates in the parent's world when isolation is on ([launcher.go](https://github.com/go-rod/rod/blob/v0.116.2/lib/launcher/launcher.go), [rod #1234](https://github.com/go-rod/rod/issues/1234)). Raw proto calls carrying the child session id, or `PageFromTarget` on the frame's target, are the workable routes.

`Network.setUserAgentOverride` is an alias of the Emulation command. Its `platform` parameter sets only `navigator.platform`, unvalidated ([Emulation.pdl](https://github.com/chromium/chromium/blob/main/third_party/blink/public/devtools_protocol/domains/Emulation.pdl)). Genuine values are `Win32`, `MacIntel` (also on Apple Silicon) and `Linux x86_64` or `Linux aarch64` ([navigator_id.cc](https://github.com/chromium/chromium/blob/main/third_party/blink/renderer/core/frame/navigator_id.cc)). **Real Chrome emits only `x86`, `arm` or an empty string for `userAgentMetadata.architecture`**; `x86_64`, `amd64` and `arm64` never occur, and 64-bit-ness travels in `bitness` ([user_agent_utils.cc](https://github.com/chromium/chromium/blob/main/components/embedder_support/user_agent_utils.cc)). rod's metadata struct has no `omitempty` on the five required fields, so any non-nil metadata sends empty strings that replace the real values, while omitting metadata leaves real client hints leaking beside a spoofed UA string ([emulation.go](https://github.com/go-rod/rod/blob/v0.116.2/lib/proto/emulation.go)). Chrome rejects a `userAgent` that fails `IsValidHeaderValue` with InvalidParams ([emulation_handler.cc](https://github.com/chromium/chromium/blob/main/content/browser/devtools/protocol/emulation_handler.cc)); that this covers CR and LF is inferred from the function's purpose. Validate at the HTTP boundary regardless, because `platform` is not checked at all.

## go-rod v0.116.2 never times out on its own

### Cleanup blocks, Kill can no-op, Close touches no process

`Launcher.Cleanup()` is an unbounded receive on the exit channel followed by `os.RemoveAll` with the error discarded. The channel closes only when the goroutine started in `Launch()` sees `cmd.Wait()` return, so **`Cleanup()` blocks forever if the browser never exits or was never launched by this launcher** ([launcher.go](https://github.com/go-rod/rod/blob/v0.116.2/lib/launcher/launcher.go)). `Kill()` always sleeps one second, **returns silently when the PID is 0**, discards all errors and does not wait for exit; the PID is a plain unsynchronised `int` assigned after `cmd.Start()`. `Browser.Close()` is only a `Browser.close` CDP call (or `disposeBrowserContext` for an incognito clone, which does not close Chrome) and never touches the launcher, the process or the user-data directory ([browser.go](https://github.com/go-rod/rod/blob/v0.116.2/browser.go)).

Every CDP call ends in a `select` on the caller's context or the reply, `rod.New()` uses `context.Background()`, and the websocket sets no deadlines and sends no pings ([client.go](https://github.com/go-rod/rod/blob/v0.116.2/lib/cdp/client.go)). A frozen Chrome with an open socket therefore blocks `Close()` indefinitely unless it is called through `Timeout` or `Context`, and those return clones, so the bound applies only to calls chained on the clone ([context.go](https://github.com/go-rod/rod/blob/v0.116.2/context.go)). Finding 5 is confirmed in full.

No documented rod pattern includes a timeout; the docs show `defer l.Cleanup()` and the maintainers' own manager does kill-then-cleanup ([custom-launch.md](https://github.com/go-rod/go-rod.github.io/blob/main/custom-launch.md), [manager.go](https://github.com/go-rod/rod/blob/v0.116.2/lib/launcher/manager.go)). The fix direction, reasoned from the source, is a bounded teardown: keep the launcher and PID beside each pooled browser, call `browser.Timeout(short).Close()` and ignore the error, call `Kill()`, then run `Cleanup()` in a goroutine selected against a timer and fall back to removing the user-data directory directly. Process and directory cleanup must never depend on `Close()` succeeding. The leaked goroutine on timeout is the unavoidable cost of `Cleanup()` having no cancel.

### A busy renderer hangs JS calls and can lock the whole browser

Chromium dispatches most CDP methods through a V8 interrupt but explicitly excludes `Runtime.evaluate` and `Runtime.callFunctionOn`, which are queued as normal tasks ([devtools_session.cc](https://github.com/chromium/chromium/blob/main/third_party/blink/renderer/core/inspector/devtools_session.cc)). On a page stuck in an infinite JavaScript loop those calls get no reply and no error. `Page.HTML()` hangs in that state because it performs a JS element lookup before reaching `DOM.getOuterHTML`.

`Page.Close()` is the sharpest case. Chromium's `Page.close` returns success immediately after merely starting a beforeunload round-trip ([page_handler.cc](https://github.com/chromium/chromium/blob/main/content/browser/devtools/protocol/page_handler.cc)); rod then waits for `Target.targetDestroyed` bounded only by the page context **while holding the browser's `targetsLock`**, the same lock `PageFromTarget` takes ([page.go](https://github.com/go-rod/rod/blob/v0.116.2/page.go)). One stuck close blocks every other `Browser.Page()`, `Browser.Pages()` and `Page.Close()` on that browser. rod's default flags include `disable-hang-monitor`. Whether Chrome 155 still force-closes such a tab under that flag, and whether `Target.closeTarget` bypasses beforeunload, are both unverified. The practical rule is to wrap every call in a context and treat a timeout on close as a poisoned browser to kill and replace.

### Eval takes a function expression, EvalOnNewDocument takes a script

rod wraps the `Eval` string as `function() { return (%s).apply(this, arguments) }` after trimming only whitespace and semicolons ([page_eval.go](https://github.com/go-rod/rod/blob/v0.116.2/page_eval.go)). The string must be an expression that evaluates to a function. Statements fail to compile, a non-function expression throws a TypeError at call time, and **an IIFE runs its body once and then still returns a TypeError**, so side effects happen while the call reports failure. `Evaluate` also retries on a missing execution context bounded only by the page context.

Effects of `Eval` die with the document. `EvalOnNewDocument` passes its string verbatim to `Page.addScriptToEvaluateOnNewDocument`, so it takes the opposite shape: a script of statements, where a bare arrow function is evaluated and discarded ([page.go](https://github.com/go-rod/rod/blob/v0.116.2/page.go)). By default the script does not run in the already-loaded document; the protocol's `runImmediately` option exists but rod's helper does not expose it, and whether v0.116.2's proto struct carries the field was not checked ([Page.pdl](https://github.com/chromium/chromium/blob/main/third_party/blink/public/devtools_protocol/domains/Page.pdl)). Keep the returned `remove` function, because registrations accumulate on reused pages.

## Pre-navigation URL checks cannot be made sound

### The validator and Chrome disagree about numeric hosts

The WHATWG IPv4 number parser uses radix 16 after `0x`, radix 8 for a leading `0` on input of two or more characters, and radix 10 otherwise; the IPv4 parser accepts one to four parts with the last part filling the remaining bytes, and tolerates one trailing dot ([URL Standard, IPv4 number parser](https://url.spec.whatwg.org/#ipv4-number-parser), [IPv4 parser](https://url.spec.whatwg.org/#concept-ipv4-parser)). The validator's `strconv.ParseUint(hostname, 10, 32)` reads `01200000001` as 1200000001, which is 71.134.140.1, while a WHATWG parser reads it as octal, which is 10.0.0.1. A local test in a WHATWG-conformant parser (Node) confirmed that mapping along with `0x7f000001`, `127.1` and `0177.0.0.1` all resolving to loopback, and a local Go 1.25.2 test confirmed the decimal reading. Chrome itself was not tested; a one-line probe on the shipped build closes that gap.

`netip.ParseAddr` and `net.ParseIP` reject every one of those non-canonical forms. The simplest strict fix follows: after stripping one trailing dot, classify the host as an IP only if `netip.ParseAddr` accepts it (then `Unmap()` and reject any zone); otherwise reject the URL if its last label is all digits or looks like `0x…`, which is exactly the standard's "ends in a number" predicate ([URL Standard](https://url.spec.whatwg.org/#ends-in-a-number-checker)). OWASP's guidance is the same in spirit: compare against the library's output value, not the input string ([OWASP SSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)).

The range list is also short. Go documents that `IsPrivate` covers only 10/8, 172.16/12, 192.168/16 and fc00::/7 and "should not be used for access control", and `IsGlobalUnicast` returns true for private space ([net/netip](https://pkg.go.dev/net/netip#Addr.IsPrivate)). A local test showed **`IsGlobalUnicast` true for CGNAT 100.64.0.1, benchmarking 198.18.0.1, 240.0.0.1, 0.1.2.3, NAT64, 6to4 and Teredo addresses**. The deny-list needs an explicit prefix table built from the "Globally Reachable = False" rows of the IANA registries ([IPv4](https://www.iana.org/assignments/iana-ipv4-special-registry/iana-ipv4-special-registry.xhtml), [IPv6](https://www.iana.org/assignments/iana-ipv6-special-registry/iana-ipv6-special-registry.xhtml)), plus whole-prefix denial of the IPv6 transition ranges that embed an IPv4 address. `Unmap()` must come first, because `Prefix.Contains` does not match IPv4-mapped addresses against IPv4 prefixes ([net/netip](https://pkg.go.dev/net/netip#Prefix.Contains)).

### Rebinding survives any check made before Chrome connects

Chrome resolves again after the validator does, follows redirects itself, and opens connections that are not requests. The CDP `Fetch` domain reports each redirect hop as a new paused request with `redirectedRequestId` set, so interception lets the server validate and fail each hop ([Fetch.pdl](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/domains/Fetch.pdl)). That closes redirect SSRF but not rebinding, because it checks a URL, not the IP Chrome dials. `Network.Response.remoteIPAddress` reports the real peer but arrives after the request has been delivered, is absent for cached responses and is the proxy's address when a proxy is set ([Network.pdl](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/domains/Network.pdl)); it is a tripwire that withholds the response body, not a preventive control. That every hop of a main-frame navigation fires `requestPaused` in the shipped Chrome was not verified empirically.

Published prior art converges on removing Chrome's egress. One project forces Chrome through a local policy proxy that resolves once, classifies every answer and dials the validated address; it found `--proxy-bypass-list=<-loopback>` and `--webrtc-ip-handling-policy=disable_non_proxied_udp` load-bearing, and reports a 456-vector harness going from 61 reachable targets to 0 (self-reported, Chrome 154) ([wp-critical-css PR #113](https://github.com/solarssk/wp-critical-css/pull/113)). Another keeps Chrome offline and fulfils every request from its own pinned fetcher ([ModPageSpeed](https://modpagespeed.com/blog/air-gapped-headless-fetch-ssrf-pinning/)). Chromium's proxy documentation supplies the reason the bypass flag matters: Chrome implicitly bypasses the proxy for localhost, 127/8 and 169.254/16, and with an HTTP proxy name resolution "is always deferred to the proxy" ([net/docs/proxy.md](https://chromium.googlesource.com/chromium/src/+/HEAD/net/docs/proxy.md)).

The fix direction, in descending strength: network-layer egress filtering for the Chrome process; an in-process Go forward proxy that resolves once and dials the validated IP, chaining to the caller's upstream proxy; and, as the weakest tier, initial-URL validation plus `Fetch` per-hop checks plus the `remoteIPAddress` tripwire, with rebinding documented as open. When the caller supplies an upstream proxy, that proxy resolves the target and the server cannot validate the address at all; the proxy URL itself is also an SSRF sink. The second and third tiers carry a latency and fingerprint cost for a Cloudflare solver that nobody measured.

**Local Network Access does not help.** It replaced the shelved Private Network Access as a permission prompt launching in Chrome 142, covering `fetch()`, subresources and subframe navigations ([Chrome for Developers](https://developer.chrome.com/blog/local-network-access)). The explainer states that "top-level navigations remain a risk", and the SSRF primitive here is a caller-chosen top-level navigation ([WICG explainer](https://github.com/WICG/local-network-access/blob/main/explainer.md)). No source found describes its behaviour in headless or automated Chrome.

### Content-Type stops CSRF but not rebinding against the local API

Under the Fetch Standard only three content types are CORS-safelisted, so a cross-origin page cannot send `application/json` without a preflight ([Fetch Standard](https://fetch.spec.whatwg.org/#cors-safelisted-request-header)). A strict media-type check therefore blocks classic CSRF, provided the server does not approve the preflight. The repo's CORS middleware emits `Access-Control-Allow-Headers: Content-Type, X-API-Key`; whether it also reflects or wildcards the origin was not read and needs checking, because a permissive preflight voids the protection.

DNS rebinding makes the request same-origin, so no preflight occurs and content-type or custom-header checks are irrelevant; Transmission's RPC (CVE-2018-5702) fell this way ([SecurityWeek](https://www.securityweek.com/code-execution-flaw-found-transmission-bittorrent-app)). The value the attacker cannot forge is the `Host` header. The fix is a Host allow-list (loopback names by default, plus an operator-configured list for Docker service names and reverse proxies), rejection of unlisted `Origin` headers, strict `application/json` on POST, CORS off by default, and an optional API key as the only control covering non-browser local callers. Host checking must be configurable or it breaks the dominant deployment, where the service is addressed by container name. No primary source recommending Host allow-listing for localhost APIs specifically was fetched; the recommendation rests on the mechanism.

### Two Go advisories reach the validator, and the toolchain is unsupported

GO-2026-5026 covers `idna.Profile.ToASCII` accepting Punycode labels that decode to ASCII; it affects `golang.org/x/net` before v0.55.0 and standard-library `net/http`, fixed in go1.25.13 and go1.26.6 ([GO-2026-5026](https://pkg.go.dev/vuln/GO-2026-5026)). The module pins x/net v0.49.0 and calls `ToASCII` on the caller-supplied hostname, so the vulnerable symbol is reached. The concrete risk is a name-based deny-list miss; whether Chrome decodes such a label to the blocked ASCII name was not tested, so the end-to-end bypass is unconfirmed. GO-2026-5970 is an infinite loop in `golang.org/x/text/unicode/norm` on invalid UTF-8, fixed in v0.39.0; the module pins v0.33.0 ([GO-2026-5970](https://pkg.go.dev/vuln/GO-2026-5970)). The advisory does not name idna as a caller, so reachability from a hostname is plausible but unconfirmed. `govulncheck` was not run and is the way to settle both.

The Go release policy supports each major release until two newer ones exist ([Go release history](https://go.dev/doc/devel/release)). **Go 1.24 reached end of support on 2026-02-10 and Go 1.25 on 2026-08-19**; only 1.26 and 1.27 are supported ([endoflife.date](https://endoflife.date/go)). Go 1.24 has missed seven security patch rounds since 1.24.13, three of them with `net/http` fixes. The go1.25.13 fix for GO-2026-5026 therefore sits on a line that is itself now unsupported. The fix: bump x/net to at least v0.55.0 and x/text to at least v0.39.0, move `go.mod` to the 1.26 language level with a current 1.26.x or 1.27.x toolchain, use `go-version-file: go.mod` in workflows, and add `govulncheck` to CI. Cheap independent guards are rejecting hostnames that are not valid UTF-8 before calling idna and making the IP check, not name matching, authoritative.

## A clearance cookie does not prove the challenge was solved

### Cloudflare documents four ways the cookie exists without passage

Cloudflare states that clearance "may be reduced or invalidated" and that a visitor "may be re-challenged, even if the cookie has not expired"; that clearance has levels and a lower level does not satisfy a higher challenge; and that **"JavaScript detections are stored in the `cf_clearance` cookie"**, so the cookie can exist on a zone where no challenge was ever solved ([Cloudflare: Clearance](https://developers.cloudflare.com/cloudflare-challenges/concepts/clearance/)). The default lifetime is 30 minutes ([Cloudflare: Challenge Passage](https://developers.cloudflare.com/cloudflare-challenges/challenge-types/challenge-pages/challenge-passage/)). Cookie presence is at best a necessary signal. The cookie-as-proof assumption is refuted by Cloudflare's own documentation, most sharply for reused sessions whose jar still holds an earlier clearance.

What stays open is whether Cloudflare deletes or overwrites a rejected cookie when it serves a new challenge. Cloudflare documents replacement only when a higher-level challenge is later solved. The project's live harness can settle this by recording the cookie value and the challenge response's `Set-Cookie` headers when a known-stale cookie is presented. The fix direction does not depend on the answer: declare success only when the interstitial is gone, and preferably when the cookie's value or expiry differs from what was in the jar before navigation. Cloudflare says the cookie is tied to "the specific visitor and device" without listing attributes; binding to IP, user agent and TLS fingerprint rests on secondary sources only.

### Interstitials need challenge-page parameters and the page's callback

No provider documents a sitekey-plus-URL token as working on a managed-challenge interstitial. 2Captcha marks `action`, `data` and `pagedata` as "Required for Cloudflare Challenge pages" and says to apply the token by executing the intercepted callback ([2Captcha: Cloudflare Turnstile](https://2captcha.com/api-docs/cloudflare-turnstile)). anti-captcha captures the `turnstile.render` parameters and passes the token to the stored callback ([anti-captcha: How to bypass Cloudflare](https://anti-captcha.com/apidoc/articles/how-to-bypass-cloudflare)). CapSolver documents challenge pages under a separate `AntiCloudflareTask` where **a static or sticky proxy is mandatory and the result is a `cf_clearance` cookie, not a Turnstile token** ([CapSolver: Cloudflare Challenge](https://docs.capsolver.com/en/guide/captcha/cloudflare_challenge/)). Cloudflare adds that Turnstile yields clearance only when pre-clearance is enabled, which is off by default ([Cloudflare: Clearance](https://developers.cloudflare.com/cloudflare-challenges/concepts/clearance/)). No provider says outright that a standalone token fails on an interstitial; the finding is confirmed in the sense that the fallback is outside every documented flow, and its real-world success rate is unverified.

The three providers name the same parameters differently, so a shared request struct is wrong for at least one of them.

| Concept | CapSolver | 2Captcha | anti-captcha |
|---|---|---|---|
| Action | `metadata.action` | `action` | `action` |
| cData | `metadata.cdata` | `data` | `cData` |
| chlPageData | not listed | `pagedata` | `chlPageData` |
| `taskId` type | UUID string | integer | integer |
| Extra status | `idle` (sample code also checks `failed`) | none | none |

All three return a `userAgent` with the token, and 2Captcha says to use it for challenge pages; a browser running a different user agent is a correctness concern worth flagging, not a documented failure.

### Schemas, polling, hCaptcha and billing

The shared `createTask`/`getTaskResult` envelope hides decoder hazards visible in the providers' own examples: 2Captcha task ids exceed 32 bits, `cost` is a JSON string at 2Captcha and anti-captcha, and anti-captcha's `solveCount` is a string although documented as an integer ([2Captcha: getTaskResult](https://2captcha.com/api-docs/get-task-result), [anti-captcha: getTaskResult](https://anti-captcha.com/apidoc/methods/getTaskResult)). CapSolver returns null error fields and an `idle` status ([CapSolver: getTaskResult](https://docs.capsolver.com/en/guide/api-gettaskresult/)). Decode only the fields used, detect errors by `errorId != 0`, and treat unknown statuses as non-terminal until the deadline. These schemas were read through a summarising fetch tool, so a quick look at each linked page before hard-coding structs is cheap insurance.

2Captcha requires waiting "at least 5 seconds" between polls and warns of temporary blocks for incorrect timeouts ([2Captcha: limits](https://2captcha.com/api-docs/limits)). CapSolver caps each task at **120 queries and 5 minutes**. A first poll at about 5 seconds and then every 3 to 5 seconds satisfies all three. `ERROR_NO_SLOT_AVAILABLE` is the only documented transient error ([2Captcha: error codes](https://2captcha.com/api-docs/error-codes)). None of the pages documents HTTP 429 or 5xx behaviour, so bounded backoff there is ordinary client practice rather than provider guidance.

As of 2026-10-11 hCaptcha is absent from the task-type listings of anti-captcha, 2Captcha and CapSolver, and the hCaptcha documentation URLs at 2Captcha and CapSolver return 404 ([anti-captcha API docs](https://anti-captcha.com/apidoc), [2Captcha hcaptcha URL](https://2captcha.com/api-docs/hcaptcha), [CapSolver HCaptcha URL](https://docs.capsolver.com/en/guide/captcha/HCaptcha/)). No discontinuation announcement was found and no live task was issued, so rejection at the API is likely but unconfirmed. Historical hCaptcha solution field names could not be verified from any live source. Treat a "task not supported" error as permanent and report it clearly. 9kw.eu still lists `hcaptcha` but does not mention Turnstile; its JSON returns `captchaid` as a string and `status` as a nested object, and its polling endpoints take the API key as a request parameter, so URLs in logs need redaction ([9kw.eu API](https://www.9kw.eu/api.html)).

No provider documents a cancel method. 2Captcha returns the price for an unsolvable task and reports `cost` on the ready result; its `reportIncorrect` is for tokens the target site rejected, with no guaranteed refund ([2Captcha: reportIncorrect](https://2captcha.com/api-docs/report-incorrect)). anti-captcha and CapSolver do not state their billing trigger. Assume an abandoned task that a worker later solves is billed, and control cost on the client: create a task only when the remaining deadline exceeds typical solve time, never run two tasks for one challenge, and cap fallback attempts per request.

## Container and CI defects are confirmed, with one refuted

### Required installs can fail silently, and the base image is expiring

POSIX gives `&&` and `||` equal precedence with left associativity, so `a && b 2>/dev/null || true` parses as `(a && b) || true` and a failure of the required `apk add` exits 0 ([POSIX Shell Command Language](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html)). A local shell test confirmed it. The image then ships without a browser and fails only at runtime. Put mandatory packages in their own `RUN` and keep stderr visible on the optional one.

The claim that Chromium is missing on armv7 is **refuted**: Alpine builds `chromium` for x86_64, aarch64 and armv7 on every branch from v3.21 to edge, and `chromium-swiftshader` exists on v3.21 armv7 ([Alpine packages](https://pkgs.alpinelinux.org/packages?name=chromium&branch=v3.21)). The real exposure is age. Chromium on v3.21 is frozen at 136 against 152 on v3.24, the package lives in the community repository that v3.21 no longer supports, and **the branch ends on 2026-11-01** ([Alpine releases](https://alpinelinux.org/releases/)). Move to `alpine:3.24` pinned by digest, and re-run the live Cloudflare probes because the Chromium major jumps by sixteen versions. The other three optional packages were not checked per architecture.

### Stale Xvfb locks crash-loop a restarted container

The X server's `LockServer()` treats an existing lock as stale only if `kill(pid, 0)` returns ESRCH; if any process holds that PID it fails with "Server is already active" ([xorg-server os/utils.c](https://raw.githubusercontent.com/XQuartz/xorg-server/master/os/utils.c)). The liveness test does not check that the process is an X server. A container restart keeps `/tmp` in the writable layer and reuses the same small PIDs, so a leftover lock looks live. That trigger is an inference from the source; it was not reproduced because the local Docker daemon was not running.

The lock is left behind when the Go process dies first. dumb-init forwards signals to the whole process group, and Xvfb unlinks its lock on SIGTERM, but dumb-init exits as soon as its direct child does, without waiting for the rest of the group ([dumb-init](https://github.com/Yelp/dumb-init), [Xserver(1)](https://xorg.freedesktop.org/archive/current/doc/man/man1/Xserver.1.xhtml)). A panic, an OOM kill or a stop timeout leaves the lock. The fix is an idempotent entrypoint: remove the lock and socket before starting Xvfb, wait for the socket rather than sleeping one second, and skip Xvfb entirely when `HEADLESS=true`. `xvfb-run -a` is the alternative; it steps around stale locks and adds an Xauthority cookie but makes the display number variable ([xvfb-run](https://salsa.debian.org/xorg-team/xserver/xorg-server/-/raw/debian-unstable/debian/local/xvfb-run)).

Chrome's headless and headful modes are unified, and old headless left the Chrome binary in M132 ([Chrome Headless](https://developer.chrome.com/docs/chromium/headless), [headless/README.md](https://github.com/chromium/chromium/blob/main/headless/README.md)). Neither source says verbatim that no display server is needed, so confirm by starting the container headless without Xvfb. Keep headful under Xvfb as the default for anti-bot fidelity; the evidence that headless is more detectable is secondary, though the project's own probe notes point the same way.

### The sandbox, the healthcheck, and the release pipeline

Puppeteer's documentation calls running without a sandbox "strongly discouraged" unless the content is absolutely trusted ([Puppeteer troubleshooting](https://pptr.dev/troubleshooting)), and this service exists to load caller-chosen URLs. Docker's default seccomp profile denies the namespace syscalls Chromium's sandbox needs unless the container holds `CAP_SYS_ADMIN` ([Docker seccomp](https://docs.docker.com/engine/security/seccomp/)), which is why containers end up on `--no-sandbox`. With it, a renderer exploit is direct code execution as the container user, with access to session cookies, proxy credentials and the container network. The pragmatic direction is a config flag that omits `--no-sandbox` for operators who supply a custom seccomp profile or the capability, with the default unchanged and documented as an accepted risk alongside compensating controls. No currently maintained seccomp profile for Chromium was found.

BusyBox `wget` resolves once, connects to a single address and has no IPv4 fallback, and Alpine 3.21's build does not prefer IPv4 ([wget.c](https://github.com/mirror/busybox/blob/master/networking/wget.c), [busyboxconfig](https://github.com/alpinelinux/aports/blob/3.21-stable/main/busybox/busyboxconfig)). If `localhost` resolves to `::1` first, the check fails permanently against a `0.0.0.0` listener while the service is healthy. That ordering comes from field reports, not musl source, so the finding is confirmed conditionally. Use `127.0.0.1` and `${PORT:-8191}`; the `--tries` and `--no-verbose` flags are ignored by BusyBox.

GitHub states that pinning to a full-length commit SHA "is currently the only way to use an action as an immutable release" and that the token should get the minimum required permissions ([GitHub secure use reference](https://docs.github.com/en/actions/reference/security/secure-use)). The tj-actions/changed-files compromise repointed version tags to a commit that dumped secrets into logs across more than 23,000 repositories ([GHSA-mrrh-fwg8-r2c3](https://github.com/advisories/GHSA-mrrh-fwg8-r2c3)). Pin every action by SHA, starting with the steps that see secrets, and add `permissions: contents: read` at workflow level with write scopes on the jobs that need them. Under `docker/metadata-action`'s default `latest=auto`, prerelease semver tags never receive `latest`; the repo's unconditional `type=raw,value=latest` line is what moves it to a release candidate, so delete that line ([docker/metadata-action](https://github.com/docker/metadata-action)). `workflow_run` fires regardless of the upstream conclusion and loses the tag ref, so gate releases by making CI a reusable workflow and using `needs:` ([GitHub workflow events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)). The lint job's `continue-on-error` and `version: latest` on action v4 mean it gates nothing; pin a v2 minor on the current action ([golangci-lint-action](https://github.com/golangci/golangci-lint-action)).

For releases, GoReleaser documents keyless cosign signing of the checksum file into a Sigstore bundle and default Syft SBOMs for archives ([GoReleaser signing](https://goreleaser.com/customization/sign/), [GoReleaser SBOMs](https://goreleaser.com/customization/sbom/)). `actions/attest-build-provenance` is now a wrapper; use `actions/attest@v4` with `subject-checksums` pointing at the checksum file ([actions/attest-build-provenance](https://github.com/actions/attest-build-provenance), [GoReleaser attestations](https://goreleaser.com/customization/attestations/)). The signing job needs `id-token: write` and `attestations: write`. For the image, Docker adds `mode=max` provenance automatically for public repositories but not SBOMs; set `provenance: mode=max` and `sbom: true` explicitly ([Docker attestations](https://docs.docker.com/build/ci/github-actions/attestations/)). BuildKit attestations are not signed by a Sigstore identity, so add an attestation or cosign signature on the image digest; whether `push-to-registry` works against Docker Hub was not confirmed.

## Conclusion

Three of the confirmed findings share one root: the server trusts a check made in one place while the behaviour is decided in another. The validator classifies a host that Chrome parses differently, the solver reads a cookie that Cloudflare may no longer honour, and the pool calls a library that waits forever on a browser it does not supervise. The durable fixes move the decision to where the behaviour happens: the egress path for SSRF, the page state for clearance, the process table for teardown. Point patches to the validator and the auth handler are still worth shipping first because they are small and the exposure is direct.

The remaining open items are all cheap to close with the project's existing live harness and one command each: Chrome's reading of `01200000001` and of `xn--<ascii>-` labels, whether Cloudflare overwrites a rejected `cf_clearance`, whether detaching releases a paused auto-attached frame, whether a hung tab closes under `--disable-hang-monitor`, and `govulncheck ./...` for the true reachable set. The dated pressure is on the base image and toolchain: Alpine 3.21 ends on 2026-11-01 and Go 1.24 is eight months past support, and both upgrades change the Chromium and stdlib behaviour that the stealth work and the validator depend on, so they belong at the front of the queue with a full probe run behind them.
